1. Linear Adoption
when I came into the project it was first a scattered QA system where the issues were tracked among various Google Sheets each team member had their own sheet where they filed bugs with their own columns and information that they chose to track . Our lead engineer as well wasn't marking issues as completed . Instead it was our job to identify which issues were completed in the new build retest those features make sure statuses were updated Etc . There is no tracking of when issues moved across various States . It was also no categories tags and other tooling . From my last roll of Builder Clarity I learned about issue tracking software and to adopt linear as our tool to track issues . It has the advantage of having very good API , strong user experience, and comments status history and timeline of the issue, a git integration, and very importantly to me an MCP tool as well as Community built CLI tools. Because our lead engineer was using Claude code for a lot of these issues - in fact, converting issues from our spreadsheet into markdown in order to triage and fix the bugs , I figured that linear would allow him to do those same actions but fetch the issue and update the issue from his agentic AI development workflow . This was very successful - the team became much more organized , was able to automate much of the bug fixing process across issue filing, triage, and implementation. Specifically bug filing and triage became entirely automated where duplicates are automatically identified and instead of creating new issues comments are appended to the existing issue . Triage attempts to identify the root cause of the issue and gives the developer the key context needed to make a decision on how the the fix should be approached 
2. Migration Adoption

One thing I noticed early on working with this team is that migrations were not tracked at all. The the development database was created by pulling the schema and data from remote and then seating the database from that state. When developers were concurrently working on different features, they'd end up with the development database based on different versions of the production database. We'd end up with conflicts and our migrations and it ended up costing us hours of debugging on more than one occasion.

1. GoHighLevel <=> JobTread integration

I created an integration between go high level and job tread to provide a white glove CRM implementation for our customers. That solved existing Gap where users weren't able to seamlessly move CRM contacts and opportunities into job tread at the appropriate pipeline stage. What I did was look into both apis for go high level and job tread and then craft a integration that used Super Bass as the back end to bridge the gap between the two platforms. I leveraged existing tooling within both platforms including go high levels automation Tools in order to make a quick proof of concept that leveraged existing features and then I created my own features when needed. 

The core of the integration was an ETL challenge from both platforms, paired with a deduplication challenge. I started by mapping out the data structures in each platform. 

- Job trend for one had a architecture as follows: each 'tenant' in the application is an organization, and each organization has many (internal) users. Each organization has many customers. Customers/accounts have many locations, locations have many jobs. Customers/accounts also have many contacts. Each job has one location. Each location has one customer. Each location has one contact. Each contact can have one user, which is the associated user object for that contact when they access the platform (like to sign a form). Each contact has an email and phone number, but these fields are both custom fields and job tread.

- GoHighLevel, on the other hand, has an architecture like this. Each tenant in the application is a subaccount (with the agency being the parent account). Each sub account have many internal users. Each organization has many contacts. Each organization also has many opportunities. Which opportunity has one contact. A new opportunity has multiple pipeline stages.

When a GoHighLevel opportunity reached a certain pipeline stage (different ID for each tenant), we want to, in JobTread, find/create a customer, contact, location, and job. Originally, I attempted to match a go high level contact to a job tread customer, as we had already used a lot of time crafting the integration design and we needed a proof of concept for our customers. Instead, in order to make the integration robust & time-saving, I decided to instead map a job trade contact to a go high level contact . The find or create logic used a waterfall Style logic gate, where first it would try to match on phone number, then email, then name. I implemented this find or create Logic for JobTread customers (since this is the parent data structure), then contact, then location, then job.  The JobTread location's contact was assigned to be the contact that I found or create and previous steps. 

From this I created more features on this platform. This integration design allowed me to ensure that I could leverage automations either way: actions from GHL to JobTread, or actions from JobTread back to GHL. 

2. RingCentral integration

Using zapier, I created a integration between RingCentral and job tread. The core need was a unified customer communication thread so that our job trade users could see all of the communication made with the customer from any member of the company. The way this was implemented was by matching the phone numbers from inbound or outbound calls/texts to jobtread contacts.  If there were multiple contacts, our integration would log Communications to each one that match the phone number. I leveraged the job tread comment thread API endpoint, creating a single thread for the overall customer Communications and depending call summaries transcriptions and action items into comments.
